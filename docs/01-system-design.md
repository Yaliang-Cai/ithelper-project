# IT Helpdesk Agent 系统设计

本系统面向遇到 IT 问题的员工，通过多轮交流、后台查询和受约束的操作推进解决过程。它使用一个业务 Agent，由自定义控制循环驱动；语义理解、状态存储、权限校验和工具执行分工明确。

设计目标是用一个规模有限但可检查的模拟企业环境，展示可靠的决策与执行边界。模型判断仍可能出错：结构合法不等于语义正确，审批有效不等于操作成功，操作成功也不总等于员工目标已实现。评估必须分别检查这些环节。

## 1 已确认的选择

| 事项 | 已确认方案 |
| --- | --- |
| 产品入口 | 简单 Web 聊天，员工是主要用户 |
| 场景 | 账号、应用、连接、权限、跨系统五类全部覆盖 |
| 数据 | 知识库、系统状态与变更、用户目录、历史解决记录、政策五类全部模拟 |
| Agent | 单业务 Agent，自定义控制循环，不使用固定业务诊断分支或多 Agent 协作 |
| 模型调用 | 新用户消息先做语义整理，再做下一步决策；同一 Agent 分阶段调用 |
| 上下文 | 后端按明确规则组织，不依赖无限累积完整聊天 |
| 多问题 | 同一聊天维护多个问题项；关联可调整，默认不合并状态 |
| 操作 | 支持实际改变模拟后台的写操作 |
| 确认 | 明确请求且符合政策的低风险动作直接执行；有影响的动作先确认；越权不能靠确认绕过 |
| 身份 | 预置演示账号，本地账号密码认证，后端绑定员工身份 |
| 审批 | 小型审批页，真实保存模拟申请及批准或拒绝结果 |
| 转人工 | 保存完整交接并停止该问题项自动处理；专家结果回流列为扩展 |
| 检索 | 关键词与向量混合，关键词作为基线及故障降级 |
| 模型供应商 | 用户后续锁定 DeepSeek Flash；Agent、模拟用户和评分统一使用 deepseek-flash，模式记录在运行配置中 |
| 记忆范围 | 当前聊天持久化；新聊天不主动检索个人旧聊天。通用历史案例仍可检索 |
| 模拟环境 | 数据定义环境，程序执行状态变更；完整故障传播模拟器列为扩展 |
| 通用知识 | 可解释现象、提出待验证假设；企业事实和操作依据必须有受控来源 |
| 排查深度 | 有新依据才追加不同修复路径；初始最多两条，不把等待反馈算失败 |
| 评估 | 规则用户、自然语言 LLM 用户和非脚本探索结合；硬检查加分维度评价 |
| 展示 | 员工页面精简；审批和开发调试视图独立 |

原先讨论中的“人工审阅”调整为由开发助手执行的 AI 辅助评审。真人盲测或 IT 专家审阅可以追加，但不作为无需用户日常介入的自动流程前提。

## 2 题目要求与交付证据

### 2.1 Problem Framing Requirements

| 要求 | 设计回答 | 交付证据 |
| --- | --- | --- |
| 谁是用户 | 普通员工，技术熟悉程度不同 | 员工聊天与角色数据 |
| 交互模型 | 账号登录后自然语言多轮交流；必要动作确认 | 真实界面演示 |
| 直接解决与转人工 | 查询、指导和目录内动作；能力或权限不足时交接 | 动作矩阵、审批和交接案例 |
| 数据来源及使用 | 五类来源，以实体和时间关联，按需查询 | 源数据、工具记录及引用 |
| 成功交互 | 员工目标满足其验收条件；分别统计审批、等待和交接 | 问题状态与评估结果 |
| 完整交接 | 保留背景、影响、证据、尝试、未决问题和责任团队 | 可读取的交接记录 |

题目中的“两分钟”是成功体验示例，不是对所有场景的统一硬性时限。报告测量实际时间，并区分模型运行时间、员工响应等待和审批等待。

### 2.2 What We Are Looking For

| 能力 | 实现机制 | 验证重点 |
| --- | --- | --- |
| Conversational diagnosis | 识别新诉求、补充、更正、反馈，必要时追问 | 短输入能推进，不反复问已有信息 |
| Multi-step reasoning | 工具反馈影响下一步；假设可修正 | 因证据变化改变诊断，而非编造解释 |
| Tool use | 原生工具调用与受控执行器 | 工具真实调用，参数和返回可检查 |
| State / memory | 原始消息、观察、问题、关联、动作分开保存 | 不遗漏问题、不混淆结果、重启可恢复 |
| Resolution vs escalation | 目标验收条件、政策与交接机制 | 假解决、漏交接、过早交接分别统计 |
| Reliability | 有限重试、结构校验、空结果、冲突和不确定执行处理 | 异常不伪装成成功 |
| Safety / guardrails | 身份绑定、动作目录、审批范围、确认绑定 | 越权及重复执行受程序约束 |
| Evaluation | 分层评测、明确事实依据、保留集与重复运行 | 过程与结果均可复查 |
| Production thinking | 日志、预算、延迟、版本与适配层 | 能定位故障与解释成本 |

最终仍须交付可运行代码、README 和演示。README 应包含选题范围、为何需要 Agent、架构、边界、模拟来源、假设取舍、启动方法、评估和改进方向。这组设计材料不替代可运行交付。

## 3 为什么需要这种架构

普通 FAQ 检索适合回答确定问题，但难以根据用户反馈修正诊断，也不管理动作前置条件和执行结果。纯规则系统能控制已知操作，却需要为大量自然语言表达和证据组合编写分支。

本系统把开放的理解和调查交给模型，把可明确验证的条件交给程序。动态的是追问内容、调查对象和顺序；固定的是身份边界、记录结构、允许动作、权限条件和执行预算。一个 Agent 可以多次调用模型和工具，不等于一次提示词调用。

不使用多 Agent，是因为当前没有必要将工作拆成多个自主角色；这会增加上下文传递和诊断责任归属的复杂度。分阶段调用有明确输入输出，但不创造多个自行协商的业务 Agent。

选择自定义循环，是为了直接观察状态、上下文与执行过程。代价是自己承担持久化、重试和恢复测试。LangGraph 的检查点和中断能力是可行替代方案；当前选择不意味着它不适合 Agent。[LangGraph 官方说明](https://docs.langchain.com/oss/python/langgraph/overview)

## 4 组件与技术默认值

以下是便于落实的工程默认值，并非已运行代码。后端建议 Python、FastAPI、Pydantic 与 SQLite；前端使用简单 HTML、CSS 和 JavaScript，由同一应用提供静态页面。这样保留一个本地启动入口，同时保持模块职责分离。[FastAPI 文档](https://fastapi.tiangolo.com/)

| 组件 | 输入与输出 | 责任 |
| --- | --- | --- |
| Web 与认证 | 登录请求、用户消息、审批操作 | 验证身份、访问权限和请求格式 |
| Conversation service | 用户事件与聊天 ID | 保存消息、安排运行、隔离会话 |
| Interpretation stage | 当前消息、问题概要、近期交流 | 提出语义观察与问题更新候选 |
| State validator | 候选更新、当前身份与版本 | 校验可写结构和引用，保存带来源记录 |
| Context builder | 运行用途、持久状态、相关证据 | 组成实际发给模型的上下文 |
| Decision loop | 上下文与工具定义 | 让模型选择查询、动作、追问或交接 |
| Policy engine | 真实身份、动作、资源、审批、确认 | 决定是否允许执行及缺失条件 |
| Tool executor | 已验证调用与操作 ID | 执行模拟查询或变更，记录真实结果 |
| Retrieval service | 文本查询、可用过滤条件 | 混合检索、降级、返回证据引用 |
| Result service | 工具收据、候选状态及回复 | 检查验收依据、呈现真实操作状态 |
| Evaluation harness | 独立场景、用户驱动器、断言 | 重置环境、运行测试、记录与评分 |

运行数据和评测数据分库存放。知识库与历史案例可用 Markdown 或 JSON 管理；可变账号、权限、会话、审批和操作记录存 SQLite。检索索引是可重建的派生数据。

建议目录职责为 app/api、app/agent、app/context、app/state、app/policies、app/tools、app/retrieval、app/storage、app/ui；data 存模拟公开数据，evals 私有保存场景与评分依据，tests 保存程序测试。具体文件名称可在实现时调整。

## 5 两阶段调用的完整过程

### 5.1 新用户消息

1. 后端验证登录和聊天归属，分配消息 ID；先保存用户原文。
2. 取得同一聊天的运行锁和状态版本，防止两个并发请求相互覆盖。
3. Context builder 为语义整理组装当前消息、近期交流、未回答的追问、问题项概要。
4. 模型返回更新候选，不直接访问数据库。
5. 程序检查结构、消息引用、对象归属和允许操作；不通过时返回有界错误，最多一次格式修正。
6. 在事务内保存候选观察与允许的记录变化；保留来源性质。
7. 为决策阶段重新组装上下文，包含用户原文和更新后的状态。
8. 模型选择工具或输出回复；工具执行前经过政策检查，结果由程序写入。
9. 工具结果加入当前运行上下文，模型可以继续调查，直到追问、返回结果、等待或达到预算。
10. 保存回复、问题进度及运行指标。结束一次运行不关闭聊天，也不自动解决所有问题。

工具结果、审批结果等结构化事件不必再调用“理解用户消息”模型。它们由相应程序记录，再按需要触发决策阶段。

### 5.2 语义整理的允许输出

允许的顶层候选操作可以收敛为：新增问题建议、追加观察、纠正既往陈述建议、问题关联建议、需要澄清的指代。具体故障描述仍用自然语言，不为所有 IT 故障创建枚举。

    {
      "observations": [
        {
          "target_issue_ids": ["I-1"],
          "category": "reported_recovery",
          "content": "用户报告 Grafana 已恢复",
          "quote": "Grafana好了"
        },
        {
          "target_issue_ids": ["I-2"],
          "category": "reported_approval",
          "content": "用户声称主管已批准申请",
          "quote": "老板说批了"
        }
      ],
      "new_issue_candidates": [],
      "relation_candidates": [],
      "unresolved_references": []
    }

当前消息 ID、操作者 ID、记录时间和 source_kind=user_report 由后端绑定。模型不能自行写 trusted=true、approved=true 或 operation_success=true。

### 5.3 程序到底校验什么

| 检查 | 可验证条件 | 不能由此证明的事情 |
| --- | --- | --- |
| Schema | 字段、枚举、大小和嵌套是否合法 | 文本内容是否正确 |
| 归属 | 问题属于当前聊天和员工 | 模型是否选中了语义上正确的问题 |
| 引用 | 原文片段确实存在于绑定消息 | 对这句话的理解是否正确 |
| 可写范围 | 此接口没有审批与执行状态写权限 | 用户陈述是否真实 |
| 幂等与版本 | 消息未重复应用、版本未冲突 | 当前诊断是否合理 |
| 状态前置条件 | 已存在规定的执行收据或批准记录 | 用户体验是否已经恢复 |

合法候选作为带来源的观察保存。错误候选不会通过改变记录类型来升级成可信后台事实。对于字段错误，模型可以修正格式；对于授权失败，不允许模型通过改写参数规避限制。

I-1 用户恢复反馈可作为其验收依据之一；I-2 用户声称获批只形成待核查观察。第二阶段应查询实际审批结果。原始消息继续保留，避免语义整理错误成为唯一输入。

### 5.4 剩余语义风险

“Grafana 好了？”可能被误解为恢复确认；“数据库那个”可能关联到错误申请。这不是 JSON 校验能完全解决的问题。第二次调用也可能重复同一模型的误判。

对涉及授权和执行的决定，必须查询后台事实。对普通问题状态，使用可追溯、可纠正的更新，并纳入错误关联和假解决评测。界面中的目标明确的“已恢复／仍有问题”按钮可提供高确定性的反馈，但不要求每次交流都通过表单完成。

## 6 上下文组织

上下文由程序中的 Context builder 组装，输入是已保存的状态、真实工具结果和当前运行目的。它不自行推断根因；语义相关性来自检索及模型候选，来源、时效、权限、预算和装配顺序由代码管理。

| 上下文部分 | 整理阶段 | 决策阶段 |
| --- | --- | --- |
| 固定指令与输出约束 | 只解释新消息，不执行动作 | 诊断、查证、行动边界与回复约束 |
| 当前用户消息 | 完整保留 | 完整保留 |
| 身份 | 已验证员工 ID、必要概要 | 已验证身份、允许范围与政策提示 |
| 问题 | 当前聊天各问题的短概要 | 所有未决项概要、当前项完整状态 |
| 历史 | 最近相关交流和未答追问 | 近期交流、尝试记录、待确认动作 |
| 证据 | 必要的引用上下文 | 当前证据内容、来源、时间和适用范围 |
| 工具结果 | 通常不需要完整重放 | 当前运行的调用与结果完整保留 |

工程默认预算：整理阶段业务上下文约 6,000 tokens，决策阶段目标约 12,000 tokens。它们是初始装配预算，不是模型上下文极限；系统指令、工具定义和当前工具循环也占用 token，必须一并计数。若必须保留的信息超预算，应暂停或重新选择调查范围，不能静默删掉授权条件。

保留优先级为：身份与强约束、当前消息、所有未解决事项、待确认与审批范围、当前问题失败尝试、最新工具结果、关键证据、近期对话、较旧辅助材料。较旧原文可通过当前聊天的历史查询工具读取。来源冲突的两边都保留，不能只挑支持当前假设的一边。

上下文输出包含各块来源 ID、版本、token 估计和裁剪记录。评测可以检查“模型错了”是否实际上是组装器漏掉了信息。过期状态可以作为历史保存，但操作前必须重新查询需要实时验证的条件。

模型协议适配与业务上下文分离。DeepSeek 思考模式工具循环需要保留其规定的 reasoning_content 和工具消息配对；不能任意删除协议字段。[DeepSeek 思考模式文档](https://api-docs.deepseek.com/guides/thinking_mode/)

建议每个新应用事件重新构建一次模型会话，把较早业务历史作为有来源的上下文数据；在该事件内部完整保留原生模型工具消息。不能将外部审批回调伪装成模型刚刚发起的 tool call。上下文重建后的引用和恢复行为需要适配器测试。

## 7 记录模型与状态

### 7.1 核心记录

| 记录 | 关键字段 |
| --- | --- |
| Message | id、conversation_id、actor、content、created_at |
| Issue | id、goal、service_refs、status、acceptance_criteria_id、version |
| Observation | issue_refs、source_kind、source_id、quote、claim、observed_at |
| Evidence | source_type、record_id、revision、content_hash、fetched_at、scope |
| Hypothesis | description、support_refs、contradict_refs、candidate 或 supported 或 rejected |
| Relation | from_issue、to_issue、type、evidence_refs、status、revision |
| Attempt | issue_id、remedy_id、normalized_parameters、evidence_refs、outcome |
| Action | action_id、actor、target、parameters_hash、authorization_refs、status、receipt |
| Confirmation | action_fingerprint、actor、issued_at、expires_at、decision |
| Approval | requester、resource、permission、scope、approver_role、status、revision |
| Handoff | issue_refs、summary、facts、hypotheses、attempts、reason、team、created_at |
| Run | event_id、model_config、prompt_version、context_refs、usage、latency、outcome |

个人聊天不自动写入通用历史案例库。通用历史是经过整理的模拟来源，避免未经验证的 Agent 输出反过来成为知识依据。

### 7.2 问题状态

| 状态 | 含义 | 允许继续的方式 |
| --- | --- | --- |
| investigating | 正在调查，有未决信息 | 查询、追问、动作或交接 |
| waiting_user | 等待员工补充或动作确认 | 员工消息或确认事件 |
| waiting_approval | 申请尚未得到有效批准 | 审批事件或查询状态 |
| waiting_external | 已知事故等外部条件尚未恢复 | 员工询问或有实际外部状态更新 |
| verifying | 动作或指导已完成，验收条件未齐 | 状态查询、用户反馈 |
| resolved | 对应目标已有充分验收依据 | 后续复发报告可重新调查并保留历史 |
| handed_off | 完整交接已保存 | 首版停止该项自动处理，可查看记录 |
| denied | 权限申请被拒绝或明确不允许 | 解释结果；新范围需新申请 |
| cancelled | 员工撤回 | 新诉求另行处理 |

denied、handed_off 和 cancelled 都不是 resolved。waiting_external 也不是“已解决”。一个聊天的整体进度由程序汇总，不让模型另存可能矛盾的 all_resolved 标记。

Run 状态另行使用 queued、running、waiting、completed、failed、budget_exhausted；一次运行结束和某个问题解决是两种状态。

### 7.3 多问题与关联

问题按可独立验收的用户目标组织，不按系统名称机械拆分。多个症状可能属于同一问题；两个权限申请通常有独立目标。

已经存在的问题默认不因“相关”而合并。共享根因、依赖、同一事故等关系独立保存；各问题仍分别验收。重复描述优先追加已有项；若重复创建，标记 duplicate_of 并保留历史，不复制执行。

语义判断只提出候选关联。明确的系统依赖可由配置支持，但“依赖存在”不证明此次故障一定沿该依赖传播。证据出现反例时可以否定关系。关系变化不得自动传播 resolved 状态。

## 8 工具与政策

### 8.1 工具目录

模型可见工具按职责保持清楚，不使用可执行任意代码的通用工具。启动时注册完整目录，按当前身份和阶段提供允许使用的工具；执行端仍再次校验。

| 工具 | 主要作用 | 关键约束 |
| --- | --- | --- |
| get_employee_context | 当前员工、设备、地点、部门与权限概要 | actor 由后端提供 |
| inspect_account | 当前员工的指定业务账号状态 | 仅关联到当前员工的账号 |
| inspect_access | 查询目标资源的实际权限 | 资源目录限定 |
| inspect_vpn | 查询当前员工 VPN 会话与可见诊断信息 | 不返回无关员工记录 |
| get_service_context | 服务健康、事故、变更和配置的可见依赖 | 返回范围与更新时间 |
| search_kb | 检索适用指南 | 返回文章与片段 ID、版本 |
| search_history | 检索整理后的通用历史案例 | 不检索其他员工原始聊天 |
| get_action_requirements | 查询动作政策与前置条件 | 与执行端使用同一份政策 |
| get_approval | 查询当前问题关联申请 | 不允许跨用户读取无关申请 |
| get_action_result | 核查操作结果，处理不确定执行 | 根据后端签发 action_id |
| read_conversation_context | 按引用读取当前聊天的旧原文 | 聊天归属检查 |
| unlock_account | 解锁允许的模拟业务账号 | 账号类型与停用原因检查 |
| grant_catalog_access | 开通资源目录内明确权限 | 按政策检查审批或直接授权 |
| reset_vpn_session | 重置当前员工模拟 VPN 会话 | 有影响，需绑定动作的确认 |
| request_approval | 创建精确范围的申请 | 去重，不接受模型指定批准 |
| create_handoff | 保存完整交接 | 保存成功才更新 handed_off |

记录观察、提出问题状态变化和生成回复属于内部受控接口，不必把每个数据库字段都暴露为模型工具。

### 8.2 统一工具返回

    {
      "ok": true,
      "data": {},
      "evidence": [
        {"source": "directory", "record_id": "E03", "revision": 4}
      ],
      "observed_at": "2026-11-02T09:00:00+08:00",
      "action_id": null,
      "error": null
    }

错误使用 code、retryable、execution_status 和安全说明。NO_MATCH、NOT_FOUND、FORBIDDEN、APPROVAL_REQUIRED、CONFIRMATION_REQUIRED、TIMEOUT、INVALID_ARGUMENT、CONFLICT、EXECUTION_UNKNOWN 分别处理，不能统一返回空列表。模型不得把错误解释成工具证实了某个事实。

### 8.3 动作边界

| 动作 | 可直接执行 | 需确认或审批 | 不允许自动执行 |
| --- | --- | --- | --- |
| 普通账号解锁 | 当前员工，普通锁定，目录政策允许 | 政策要求的额外验证未满足则停止 | 安全停用、他人账号、重置 MFA |
| 标准 Grafana 只读权限 | 部门符合且员工明确请求 | 目标或范围不明确先澄清 | 管理员角色或任意资源 |
| 目录内生产只读权限 | 不直接执行 | 有效资源负责人审批，范围与请求一致 | 生产管理员、写入权限等未开放动作 |
| VPN 会话重置 | 不由含糊故障描述直接触发 | 告知影响并取得对应动作确认 | 操作他人的会话 |
| 生产服务或流水线修改 | 无 | 首版即使获批也不开放对应工具 | 生产回滚、任意命令、重启关键服务 |

工具目录决定“能否做”，审批决定“是否获得某项允许动作的额外授权”。批准不能创造原本不存在的工具能力。

用户明确请求的低风险动作可以直接执行，但程序不可能只凭 Schema 证明自然语言授权成立。低风险动作仍存在意图误判风险，必须限制目标和影响范围并做评测。具有连接中断等影响的动作，用明确展示对象及影响的确认卡绑定 action_fingerprint；动作或目标变化时原确认失效。

### 8.4 幂等和不确定执行

幂等键由后端依据持久 action_id 生成，绑定员工、问题、动作和规范化参数。API 重试、刷新和重复审批事件复用同一操作记录。不能用模型自行生成的随机键来声称避免重复执行。

模拟数据变更和操作收据在同一数据库事务中提交。评测故意支持“已提交但响应超时”：此时调用方看到 EXECUTION_UNCERTAIN，先 get_action_result 查询，不能盲目再次执行。

检查与变更尽量在同一事务内使用版本条件；确认或审批已失效、权限被撤回、资源状态变化时重新判定。对于不同操作之间的业务撤销，不承诺自动回滚所有动作；只对明确可补偿的模拟操作设计补偿规则。

## 9 身份与授权

帮助台登录与模拟 Okta 登录是不同系统，通过员工 ID 关联。员工可以用帮助台账号报告 Okta 锁定；这是原型的身份假设，不等价于企业生产环境中的独立强身份验证。

预置演示账号使用密码哈希保存；建议成熟 Argon2id 实现，不保存明文密码。密码不进入模型上下文、普通日志或评测 trace。[OWASP 密码存储](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

后端会话通过 HttpOnly Cookie 关联用户。登录重建会话 ID，退出使其失效；写接口验证 CSRF，部署 HTTPS 时使用 Secure Cookie；本地开发的配置差异要写进 README。[OWASP 会话管理](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

employee 只能访问自己的聊天和申请；approver 只能处理其负责资源的申请，默认不允许批准自己的申请。调试权限单独控制，不能仅靠前端隐藏按钮。请求中的 user_id 不能覆盖后端身份。

切换账号不继承前一账号的聊天、确认或工具执行上下文。同一员工可以重新打开自己的旧聊天；新建聊天不会自动读取旧聊天内容。

## 10 审批与人工交接

### 10.1 审批闭环

申请绑定请求人、目标资源、具体权限、理由、相关问题、政策版本和有效期。状态为 pending、approved、rejected、expired、cancelled；执行状态另外记录。

审批人通过自己的账号批准或拒绝。测试时由驱动器使用同样的权限路径提交审批，而不是直接修改 approved 字段。重复决策有幂等检查；终态冲突返回错误。

工程默认采用后端持久事件驱动恢复：批准事件写入待处理运行，由同一应用的处理器读取；不依赖浏览器一直打开，也不保持一条 LLM 请求等待审批。事件处理仅恢复关联问题和已授权动作，不给审批人会话附加员工身份。

恢复时重新读取员工是否有效、当前政策、批准范围、有效期、撤回状态和执行记录。原申请是针对该动作的持续请求，退出聊天本身不撤回它；员工可以明确取消申请。需要实时用户确认的动作仍需满足确认条件。此自动恢复方式是工程默认值，若改为员工点击继续，应同步修改界面和评测。

### 10.2 人工交接终点

交接内容包括：员工目标及影响、已知事实、证据来源、尝试与结果、未验证假设、缺失信息、转人工原因、建议团队、相关问题 ID 和必要对话引用。后台检查字段存在、引用有效、敏感信息范围；语义完整性仍需评估。

只有记录持久化成功才进入 handed_off。首版没有真实 IT 队列或专家接单，所以界面应说“已创建模拟交接记录”，不能声称真人已接单或承诺响应时间。

该问题停止自动诊断和修复，其他问题照常推进。首版不处理专家补充结果后的自动恢复；相关设计见扩展材料。

## 11 诊断与结果判断

每次调查应服务于一个未决点。优先查询系统已有信息，再询问员工独有的信息。一般一次问一个重点问题，两个紧密相关的问题可以合并。员工短输入、拼写错误和非专业表述都是正常情况。

通用 IT 知识用于解释和提出假设；改变配置、命令执行等具体操作建议必须来自适用的已审阅指南。引用本身不保证适用，模型需要核对服务、版本和前置条件。政策不允许的行为不能通过让员工手工执行来绕过。

第一次修复失败后，只有新证据或另一条明确适用路径才允许追加。初始上限为每问题两条不同修复路径；查询和等待反馈不占修复次数。remedy_id、参数与预期作用用于识别重复，语义上是否实质不同仍是评测重点。

工程初始预算为每次用户事件最多 8 次模型请求和 12 次工具执行，含格式修正；只读工具最多额外重试一次，写操作不盲重试。单次模型请求初始超时 45 秒，单次运行总上限 120 秒，均以实测调整。这些是停止无限运行的硬上限，不是期望延迟目标。

触发转人工的原因应可解释：员工明确要求、必须操作不开放、无法安全继续、缺少关键证据且可行替代已用尽，或合理尝试后无进展。达到单轮预算只说明本轮停止，不自动证明能力不足。

已知事故且影响范围匹配时可以进入 waiting_external，提供经过证实的事故信息和适用临时办法；不要求每个事故都另建个人交接。影响范围不匹配时不能直接归因。

| 目标 | 验收条件示例 |
| --- | --- |
| 解锁账号 | 后台普通锁定解除；若目标是恢复登录，还需登录验证或明确用户恢复反馈 |
| 开通权限 | 目标权限存在且范围正确；若用户诉求包含访问页面，则继续验证访问 |
| VPN 恢复 | 连接恢复并达到案例定义的观察窗口，不能仅凭重置返回成功 |
| 应用故障 | 员工对应症状恢复，或可观测指标满足目标条件 |
| 跨系统故障 | 每个独立用户目标分别验收，根因相关不传播成功状态 |

明确正向用户反馈可以成为验收依据，但其语义解释仍依赖模型。反馈含糊或与最新后台结果冲突时，不自动标记 resolved。测试环境通过确定的模拟状态检查用户模拟器有没有虚构恢复。

## 12 五类数据的组织

建议初始准备 20 篇知识文档、12 条历史案例、6 位演示员工、8 个服务、若干事故和变更记录、约 12 条政策。数量是工程起点，覆盖和一致性比数量重要。

员工覆盖销售、远程办公、数据工程新人、平台工程师和资源审批人等角色。所有来源通过 employee_id、service_id、resource_id、region、device_version、change_id 关联。

| 来源 | 必要元数据 | 有意设计的难点 |
| --- | --- | --- |
| 知识库 | 服务、症状、适用版本、前置条件、有效时间、审阅状态 | 同主题新旧版本、不可直接适用文章 |
| 状态与变更 | 服务、区域、开始时间、最近观察、受影响组件 | 状态页延迟、地区不匹配、维护仅有时间相关性 |
| 用户目录 | 部门、角色、地区、设备、权限、账号标识 | 新员工缺少权限、不同地区不同配置 |
| 历史案例 | 当时环境、症状、验证根因、解决步骤、结果 | 症状相同但原因不同、环境已变 |
| 政策 | 动作、资源、直接允许条件、确认、审批角色、禁止条件 | 紧急诉求不改变授权，申请范围变更 |

每条合成数据注明模拟属性。采用固定场景时钟，使“昨天”“上周五”等相对时间可复现。演示环境可设置 as_of 为 2026-11-02 09:00 Asia/Shanghai；评测场景分别设定时间，不依赖执行主机当天日期。

后台只按配置和操作规则变化，不识别员工输入是否匹配某段演示台词。面试新问题照常经过模型、查询和政策检查；没有模拟的数据应报告未知，不临时编造企业记录。

预期答案、隐藏根因和故障注入配置仅在评测侧可见。实际工具只能返回其职责允许观察到的信息，不直接附带“本例正确答案”。

## 13 混合检索

知识库和历史案例使用 BM25 与 embedding 检索。用户目录、状态和政策优先按 ID 与字段查询，不强行全部向量化。

文档按自然小节切分，保留标题、父文档、适用版本和前置条件。初始片段约 300 至 600 tokens，长操作步骤保持完整或提供父段读取，避免只检索到动作而丢失限制。

查询同时进入关键词和向量两路，初始各取 10 个结果；按排名融合后保留约 5 个，按父文档去重。RRF 初始使用 1/(60+rank) 累加，仅作为可调整参数，不把排名分数当正确性概率。中文分词需保留英文产品名、错误码和版本号；不能直接采用只适合英语空格切分的处理方式。

过滤只使用已知条件；员工未说明版本时不能猜版本再强过滤。返回 NO_MATCH 是合法结果，不为凑足 Top K 返回无关文档。相似度阈值需要开发集校准，不能未经测试写成通用可信度。

建议 BM25S 本地执行；向量使用硅基流动 BAAI/bge-m3，缓存文档向量，本地计算相似度。2026 年 11 月 2 日重新核对的官方价格页标为免费，用户提供独立密钥后的实际调用已返回 1024 维向量。不自动切换到收费的 Pro/BAAI/bge-m3；服务价格与可用性仍以供应商当时规则为准。[价格页](https://siliconflow.cn/pricing) [模型说明](https://huggingface.co/BAAI/bge-m3) [BM25S](https://github.com/xhluca/bm25s)

索引保存 embedding 模型标识、维度、文档哈希、切分版本和索引版本。查询与文档必须使用同一向量空间；更换模型要重建索引，不能混用缓存。

embedding 服务不可用时明确降级到 BM25，记录 degraded=true。不能把降级运行归入正常混合检索结果；缓存未命中的查询失败仍可使用关键词路径。Reranker 不是首版必需项。

## 14 五类场景的端到端示例

### 14.1 账号

员工说“又登不进去了，密码改过了”。先识别具体系统或查已有上下文，保存“已改密码”，避免重复建议。查询账号和服务状态。普通锁定符合政策时执行解锁；MFA 故障或安全停用则走对应安全指导或人工交接。解锁成功后继续验证登录。

### 14.2 应用

员工说“Salesforce 太慢了”。询问影响范围前先查看员工地区和事故记录。有同地区事故并不等于所有个人问题都由事故导致，核对症状与时间。无事故时查询适用指南和近期变更，指导安全检查。确认事故后报告 waiting_external，不称已修复。

### 14.3 连接

员工说“VPN 十来分钟就掉”。查询客户端、会话和已知故障，询问后台无法获得的家庭网络情况。如果适用路径要求重置会话，先呈现影响及确认；执行后检查会话，并等待必要的持续观察。存在基础网络问题时，重置不能神奇治愈。

### 14.4 权限

员工同时申请 Grafana 和 Snowflake。建立独立目标，读取目录与政策。标准只读权限符合条件可执行；生产只读按政策申请审批。一个完成、一个等待时分别呈现。员工声称获批不改变审批记录。

### 14.5 跨系统

员工报告 Jenkins 超时与 Tableau 陈旧。检查维护、服务依赖、运行状态和历史案例；维护时间相近只形成候选关联。若需要生产网络变更，生成包含支持和反对证据的交接，停止该项自动修复。若一项恢复而另一项仍旧，分别记录。

## 15 界面与 API 默认设计

员工界面包含聊天、问题进度、动作确认卡、审批或交接编号，以及可展开的相关证据。语言跟随员工输入，支持中英文；默认回复简短，复杂步骤分段给出。用户可以结束或重新打开聊天，Agent 不关闭前端。

审批界面只显示当前审批人有权处理的申请。调试视图独立，显示实际上下文、工具、状态差异、错误和耗时；敏感凭据排除。简短决策依据可以显示，模型内部思考文本不作为审计证据。

| API | 职责 |
| --- | --- |
| POST /auth/login 与 /auth/logout | 登录和退出 |
| GET /me | 当前身份 |
| POST /conversations | 建立当前员工的聊天 |
| GET /conversations/{id} | 读取有权访问的历史 |
| POST /conversations/{id}/messages | 保存消息并创建运行 |
| GET /runs/{id}/events | 通过 SSE 或轮询读取进度 |
| POST /confirmations/{id}/decision | 对绑定动作确认或取消 |
| GET /approvals 与 POST /approvals/{id}/decision | 有权限的审批查询和决策 |
| GET /handoffs/{id} | 读取有权查看的交接 |
| GET /debug/runs/{id} | 开发模式查看执行记录 |

没有被授权的请求不能只靠猜测 ID 读取资源。输出中的 HTML 不直接信任模型内容，避免在聊天渲染中执行脚本。

## 16 故障与可观测性

| 故障 | 处理 |
| --- | --- |
| LLM 不可用或超时 | 保留消息和状态，说明本次未完成；不编造诊断 |
| 非法结构化输出 | 一次有界格式修正；仍失败则记录模型协议错误 |
| 工具读超时 | 有限重试或有依据的替代来源，标明缺失 |
| 写操作结果不明 | 查询 action_id 的实际执行记录 |
| 检索无结果 | 承认缺少依据，允许安全假设和针对性追问 |
| 来源冲突 | 保存冲突双方，核对时间和范围；不掩盖反证 |
| 数据库保存失败 | 不声称审批或交接已创建 |
| 并发消息 | 同一聊天运行串行化或使用版本冲突重试 |
| 应用重启 | 读取持久事件和操作收据，先核查在途动作 |
| 预算耗尽 | 停止本轮，保留进度；是否转人工另行判断 |

每次运行保存 trace_id、阶段、模型和配置、提示词版本、数据与政策版本、上下文引用、工具调用及结果、状态变化、tokens、耗时和降级标记。用户模拟及评分调用与业务 Agent 调用分别计费统计。

成本按实际 API 用量和执行时费率计算。请求数不是 token 成本的替代；缺少 reasoning 或缓存计费细节时报告估算范围，不能伪造精确费用。

## 17 验证顺序与实现边界

先验证程序边界：身份隔离、审批与确认、幂等和状态转换。再接模型，用少量困难案例检验信息提取、问题映射和上下文装配。随后补齐五类数据与动作，最后执行正式评估和演示准备。

这不是承诺所有模型判断都准确。每一步须保留失败案例，判断问题来自数据、检索、上下文、模型、政策、执行还是用户模拟器。分阶段调用增加延迟和错误传递风险；未做对照时，只能说它使责任分解更清楚，不能声称已证明更准确。

日常开发和评估可由开发助手执行。用户需要提供可用模型凭据并确定调用预算；若外部账户异常或必须由账户所有者操作，仍需要用户介入。凭据在本地配置，不写入仓库或设计材料。

正式测评的详细场景、断言和评分见 02-evaluation.md。生产化与扩展见 03-defense-and-extensions.md。
