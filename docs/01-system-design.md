# 系统设计

系统服务于遇到 IT 问题的员工。聊天、审批和确认都进入持久事件，由一个 Agent 持续处理。模型决定调查和建议，业务代码决定记录与操作是否有效。

## 模块职责

| 模块 | 责任 |
| --- | --- |
| `app/main.py`、`auth.py`、`ui/` | 登录、会话、员工聊天、审批和调试界面 |
| `worker.py`、`storage.py` | 事件领取、租约恢复、SQLite 持久化 |
| `agent.py`、`prompts.py`、`contracts.py` | 解释消息、工具循环、结构化提议与停止条件 |
| `context.py` | 按当前身份和问题组织上下文，保留批准、拒绝、尝试及反馈 |
| `domain.py` | 问题状态、证据归属、验收、批准与确认、幂等和事务 |
| `tools.py`、`retrieval.py` | 结构化业务查询、受限操作、知识库与历史检索 |
| `providers.py`、`budget.py` | 供应商请求、费用预留和结算 |
| `evals/`、`tests/` | 场景驱动、用户模拟、结果断言、辅助评分与程序回归 |

## 一轮对话

用户消息先保存并建立事件。模型把当前消息解释为新问题、补充信息、反馈或纠正；程序检查引用和归属后记录。Agent 读取当前上下文，调用工具，结合结果继续查询或提问，最后提出回复和各问题的状态更新。批准与确认通过独立事件恢复同一处理循环。

消息原文、用户陈述、系统证据、推测、操作收据分开保存。用户声称“已批准”不能替代审批记录，历史相似案例不能证明当前根因。问题之间可以记录关联，各自保留状态和验收条件。

## 执行与验收

工具范围限定为本人普通账号解锁、受限会话重置和目录只读授权。业务事务核对精确目标、当前身份、政策和授权状态；模拟业务变更与操作收据一起提交。真实外部系统无法共享这个事务，后续需要单独对账。

验收按目标区分：账号解锁查当前账号；登录体验恢复还需用户反馈；权限查精确资源的实际授权，需要使用验证的目标还需反馈；VPN 检查观察窗口和反馈；应用恢复检查当前服务状态、匹配事故与恢复反馈。审批、等待外部恢复和交接不算解决。

执行结果不确定时先查询操作记录。问题复发会使旧的恢复反馈失效；下一种修复需考虑最近尝试和新的失败反馈。提交多项状态时整体校验，失败则整批回滚，避免部分回复与状态不一致。

## 主要取舍

| 选择 | 原因 | 代价 |
| --- | --- | --- |
| 单 Agent，两阶段调用 | 理解与动作错误可分开检查，无需角色协调 | 额外调用；未证明比单阶段更准确 |
| 程序组织上下文 | 当前身份、授权、未解决问题和失败反馈可追溯 | 长对话可能超限；当前不做跨聊天个人记忆 |
| 关键词与向量混合检索 | 兼顾精确系统名和自然语言表达 | 多一个供应商依赖，需记录关键词降级 |
| SQLite 与模拟适配器 | 本地运行简单，操作过程可复现 | 不代表多副本并发与真实外部操作可靠性 |
| 有界调用与有限修复尝试 | 防止循环调用、重复操作和失控费用 | 复杂问题可能提前停止，需要保留进度或交接 |
