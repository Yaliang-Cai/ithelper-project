# IT Helpdesk Agent：取舍、答辩与扩展

> 交付说明（2026-11-02）：本文保留原选择理由和扩展边界，不把规划当成绩。当前唯一授权LLM已锁定deepseek-flash，embedding固定BAAI/bge-m3；不是待选供应商。真实程序/模拟背景/fixture/实时模型模式在[交付证据](delivery-evidence.md)分别记录；[实测报告](evaluation-report.md)保留原失败，不能声称通用语义正确或最终30全通过。七项工程裁定的理由和错误代价见[决策记录](engineering-decisions.md)。专家接续、个人跨聊天记忆、传播仿真、真实企业接入仍未实现。

本文解释为什么这样设计、哪些收益尚未被验证，以及以后增加能力时应如何保持边界。它与系统设计、评估设计共同构成方案材料；文中的效果均为设计目标，实际效果须以实现和实验记录为准。

## 1 项目的核心主张

项目要证明的是：一个 Agent 能否在有限的企业环境中，持续理解员工目标，利用不同来源调查，在权限内执行并核查结果，处理不了时交接足够的信息。

“模型决定下一步调查什么；程序决定允许做什么、何时必须停止，以及何种证据才算解决”是分工原则，但最后一句需要进一步限定：程序能检查验收证据的类型、来源和必要条件，不能完全证明自然语言反馈的含义。用户说“那个好了”究竟指什么，仍可能需要澄清。

题目确实不要求每个维度都完善。但这不意味着只讲取舍、不运行关键能力。合理的交付是：关键路径能够真实执行，边界能够被测试，未完成的能力说明影响，方案优劣由可观察结果支持。

## 2 核心选择的收益、代价与替代方案

| 选择 | 为什么选择 | 代价或局限 | 什么情况下重新考虑 |
| --- | --- | --- | --- |
| 单业务 Agent | 调查目标集中，减少角色之间的信息传递 | 一个模型可能连续犯同一种错误 | 不同业务域确实需要独立权限、上下文与职责时 |
| 自定义控制循环 | 过程透明，便于解释和记录实际状态 | 要自己做好恢复、重试和并发 | 长流程、持久任务和外部事件显著增多时评估框架 |
| 两阶段调用 | 语义候选与下一步行动分开观察，便于归因 | 多一次调用，可能传播或重复语义错误 | 实验证明收益不足时可合并，保留记录和校验边界 |
| 多问题独立状态 | 一个目标恢复不会覆盖其他目标 | 模型需要处理拆分、重复和指代 | 只面向单一事务产品时可以简化 |
| 五类小规模来源 | 可以演示实体、范围、时效和反证之间的关系 | 数据质量设计工作多，覆盖仍有限 | 若某来源没有实际决策价值，应减少冗余数据 |
| 混合检索 | 同时覆盖精确名称、错误码与语义表达 | 多一个供应商依赖和索引流程 | 对照显示无实际收益时保留关键词方案 |
| 模拟业务写操作 | 可以验证前置条件、真实变更与验收 | 不能证明真实企业 API 已被正确集成 | 获得真实系统沙箱及明确授权后添加适配器 |
| 独立审批角色 | 审批不由模型自行宣布，范围可校验 | 增加后台事件与恢复逻辑 | 审批系统外接后仍保留这些约束 |
| 当前聊天记忆 | 支持多轮与重启，身份隔离容易检查 | 新聊天不能自动回忆个人旧问题 | 重复报障成为主要需求且访问治理准备好时 |
| 配置驱动的模拟环境 | 能快速重置并得到确定的操作结果 | 不模拟完整的依赖传播、网络和故障机理 | 需要评估复杂恢复链路时扩展模拟器 |
| AI 辅助评审 | 可自动运行，减少日常人工参与 | 存在评分偏差，没有专家验证 | 真实试点前补专家抽查与实际员工测试 |
| 简单聊天与独立调试页 | 员工容易使用，评审者仍能检查过程 | 不是完整服务台产品 | 业务开始需要队列、工单 SLA 和通知时 |

不能把表中的收益全部写成已经实现的效果。例如，两阶段调用改善了可检查性，不代表已经证明准确率提高；混合检索扩大了匹配方式，不代表一定提高任务成功率。

## 3 哪些部分是真实逻辑，哪些部分是模拟

| 层面 | 真实运行的内容 | 模拟内容 | 不能据此声称 |
| --- | --- | --- | --- |
| 登录 | 密码校验、服务端会话、角色与归属检查 | 预置员工和审批人 | 已接入企业 SSO |
| Agent | 实际模型请求、工具选择、上下文与状态更新 | 企业背景和测试问题 | 已覆盖真实员工表达分布 |
| 检索 | 实际关键词、embedding 与排序 | 自建知识文章与历史案例 | 在大规模企业知识库上同样有效 |
| 操作 | 政策检查、事务、幂等、模拟状态变更 | Okta、VPN、权限等后台 | 真实系统集成已经可用 |
| 审批 | 创建、批准或拒绝、权限检查与审计 | 公司组织与审批规则 | 已满足企业完整审批治理 |
| 测试 | 实际测试驱动、真实模型模式和结果检查 | 用户、事故、故障注入、评分参与者 | 已有真人盲测或专家背书 |

使用模型响应 fixture 的测试也有价值，但只验证程序在给定响应下的行为，不能证明模型会自己产出该响应。正式结果必须区分 fixture、规则用户加真实 Agent、LLM 用户加真实 Agent 三种运行模式。

## 4 答辩时可以展示的证据

建议按“诉求—事实—决定—执行—结果”的顺序讲一个完整案例，再展开架构。展示员工原文、关键工具输入输出、来源版本、执行前置条件和最终问题状态即可，不需要展示隐藏思维链。

证据应来自真实运行保存的记录，而不是事后让模型补写解释。可以展示简短的决策依据字段，但它只是模型给出的依据摘要，仍要和当时可见证据及实际动作对照。

一个有说服力的示例是员工同时申请 Grafana 和生产数据库权限：模型识别两个独立目标，读取实际权限和政策；允许的标准权限被开通并核查；生产权限等待真实审批事件；两个目标的状态始终独立。审批通过后还要执行与验收，不能直接把申请标成已解决。

## 5 演示安排

以下时间只是演示建议，不是题目要求或系统性能承诺。每个示例使用一键重置的数据环境，允许演示者自由改写输入。

| 顺序 | 演示内容 | 观察重点 |
| --- | --- | --- |
| 1 | 普通账号锁定，完成允许的解锁 | Agent 确实查询、执行、核查，没有只输出操作说明 |
| 2 | Grafana 与生产库同时申请 | 多目标、直接执行与等待审批并存 |
| 3 | 切换审批人批准，再回到员工 | 后台批准事件、精确范围、一次执行、状态更新 |
| 4 | VPN 已尝试一次仍掉线，随后拒绝重置 | 保留失败反馈，尊重确认，不机械重复 |
| 5 | Jenkins 与 Tableau 维护后异常 | 多源支持与反证，关联不合并状态，必要时交接 |
| 6 | 临时输入或故障注入 | 展示工具超时、越权请求或不明确指代的处理 |

时间有限时可挑三个完整案例，其余通过评测记录呈现。选择演示案例不改变五类场景的实现与评测范围。保留一个实际失败及修复记录，比只展示顺利台词更能说明判断质量。

演示前检查：服务能够按 README 启动，默认账号可登录，模型和检索模式明确，数据可以重置，审批及调试角色可访问各自界面，网络失败能被正确说明。没有可用模型 API 时只能演示 fixture 模式，并明确其限制。

## 6 常见追问与回答边界

### 6.1 有固定控制循环，还算 Agent 吗？

算。运行边界和工具接口是固定的，调查步骤由模型根据证据选择。同样一句“登不上”，可能进入账号锁定、服务事故、MFA 或用户操作指导等不同路径。需要用不同环境下的实际调用轨迹证明这种适应，而不是仅凭名称判断。

### 6.2 为什么不直接写一个很长的提示词？

提示词可以描述任务和判断原则，但不能替代权限检查、持久状态、事务与预算。这里把稳定的业务边界放入代码，把当前事实放入有来源的上下文，提示词只承担有限阶段的行为约束。提示词仍需要认真设计与测试，并非越短越好。

### 6.3 既然程序校验了，为什么还会误判？

程序知道某条引用是否存在、某个问题是否归当前员工、某次批准是否有效，却未必知道“那个问题”究竟指什么。方案用原文保留、目标明确的反馈、必要澄清、可纠正记录和语义评测控制风险，不能声称完全消除。

### 6.4 两次调用是不是相当于两个 Agent？

这里是同一个业务 Agent 的两个阶段，没有独立目标、自主协商或互相委派。分阶段是为了限制各次调用的职责和写入范围。不能把第二次调用视为独立验证，也没有预先证明它比一次调用准确。

### 6.5 谁决定上下文怎么组织？

后端 Context builder 按阶段、状态、来源、时效和预算装配。模型可以提出相关问题或发起检索，但不能自行决定哪些授权规则被删掉。每次实际发送的上下文有引用清单，错误时能检查是否漏传证据。

### 6.6 五类来源是否只是为了凑数量？

应该避免。知识库给可执行步骤，状态与变更说明当前影响，目录限定员工与设备，历史提供可参考但不等同当前事实的经验，政策决定能否操作。每类数据都应至少在某个案例里改变下一步选择；不要求每次咨询都调用五类。

### 6.7 DeepSeek 是否一定够用？

目前只能说它是优先验证的供应商。能否满足要求，要看具体模型、工具调用、结构输出、中文短输入、多目标状态和异常处理的实际评测。同一项目换模型可能影响结果，必须记录配置并保留基线。没有实测前不作保证。

### 6.8 免费 embedding 是否意味着项目不需要费用？

不意味着。embedding 服务的可用免费档、额度与账号条件需要接入时确认；业务模型、用户模拟和评分都可能产生费用。关键词降级可以保留可用性，但不是正常混合模式的实验结果。

### 6.9 什么时候算解决，什么时候算转人工？

解决对应具体目标的验收条件，不能统一成“工具成功”。开通权限要验证准确资源和权限；体验故障还需要员工反馈或规定的观察。转人工必须保存完整交接且明确原因；已知事故等待恢复属于另一种状态。

### 6.10 为什么不是遇到困难就交接？

过早交接会让系统缺乏实际价值，所以评测同时衡量可解案例的完成和必须交接案例的正确处理。遇到权限限制、明确人工请求、没有可靠路径或连续不同路径失败才按政策交接。单次预算耗尽可暂停，不自动等同于业务能力不足。

### 6.11 自动评估会不会自问自答？

会有这种风险。通过用户事实卡与隐藏 oracle 分离、数据库断言、评分证据、模拟器有效性检查和保留变体减轻它。但设计者和评审者都是 AI 时仍可能共享盲点，所以如实称为合成评估与 AI 辅助评审。

### 6.12 AI 开发是否意味着用户完全不用介入？

日常编码、测试编写、场景生成、审批驱动和结果分析可以自动完成。账号所有者仍需提供可用的本地 API 配置及费用边界，可能需要完成供应商账号验证。答辩者需要理解关键取舍与局限，不能只背结论。这些不等于要逐条手工测试或评审。

## 7 扩展一：跨聊天个人记忆

当前聊天记忆已覆盖多轮和重启；下面是未纳入当前实现的扩展，不与可检索的通用历史案例混为一谈。

### 7.1 收益与准入条件

重复报障时可以少问已经说过的信息，发现同一员工的复发问题，并延续未完成背景。代价是更多个人信息治理、过期事实和错误延续风险。只有重复报障产生可测收益，且身份与删除策略清楚时才值得启用。

### 7.2 数据与检索设计

增加 PersonalMemory 记录：employee_id、source_conversation_id、source_message_refs、issue_goal、verified_outcome、device_refs、observed_at、expires_at、revision、visibility。摘要必须保留来源，不把推测写成事实。

增加 search_own_history 工具，由后端绑定员工，先限定归属，再做语义与关键词检索。访问控制在服务端查询层和返回层检查；不能只靠向量 metadata 或提示词。没有权限的记录不进入候选结果或模型上下文。

旧记忆作为背景，不作为当前设备状态、当前授权、有效审批或操作确认。模型可说“上次记录显示……”，当前动作仍查询新状态。用户更正、删除或过期时，索引与摘要一同更新；保留删除事件的最少审计信息，不保留被要求删除的全文副本。

### 7.3 对话行为与评估

新聊天仅在当前问题有明确相关性时查询，不主动暴露无关历史。记忆条目与当前陈述冲突时说明时间与差异，不能坚持旧结论。

比较启用前后的必要追问数、复发识别和错误延续率；测试跨账号泄露、员工离职、设备更换、旧审批重用、更正和删除后检索。收益不能只用“检索到了历史”衡量。

## 8 扩展二：完整故障传播与恢复模拟器

### 8.1 收益与代价

完整模拟器可以表达一次底层故障影响多个服务、修复后分阶段恢复以及新的副作用。当前配置环境已经能测试具体状态变化，但不会自动模拟所有依赖链。扩展需要维护更复杂的世界规则，本身也需要测试，不能让模拟器错误被误认为 Agent 错误。

### 8.2 组件设计

增加 ServiceNode、DependencyEdge、Fault、ScheduledEvent 与 WorldSnapshot。节点包含可观测健康和隐藏原因；边说明依赖条件；事件按受控逻辑时钟执行。用固定规则和随机种子决定传播、延迟与恢复，LLM 不充当事实裁判。

动作经同一工具执行器进入模拟器，再由规则计算后续变化。例如修复身份令牌服务可以恢复 Jenkins 的认证，但 Tableau 仍需下一次数据刷新。这保留两个目标的独立验收，避免“共同原因已修好，所以全部立即正常”的错误。

业务 Agent 只得到工具允许观察的信息；隐藏故障和传播真值仅供评测。测试用户只看到自身实际体验，不得到整个依赖图的隐藏解释。

### 8.3 验证方式

先用确定性单元场景检查模拟器自身的事件顺序和状态转换，再评估 Agent。固定输入应产生可重放世界事件；不同修复路径允许有不同正确轨迹。保留不相关维护和同时发生的独立故障，防止 Agent 学会“时间接近就是因果”。

## 9 扩展三：专家补充后恢复 Agent

当前 handed_off 状态结束该问题的自动处理，专家回流属于未来能力。

增加受认证的 expert_update 事件，绑定交接 ID、问题 ID、作者权限、内容类型、证据和版本。信息可以是补充事实、请求继续调查、已完成操作的外部收据或结案意见；不是所有专家文字都能直接成为后台状态。

明确的恢复请求将该问题置回 investigating 或 verifying，再重新构建上下文与检查政策。旧操作确认、过期审批和被撤回目标不能随恢复自动复活。专家完成的外部操作以可核查收据记录，缺少证据时保持来源性质。

并发控制检查交接版本、当前负责方、用户撤回与重复事件。状态变化通知员工，避免员工以为仍由人工负责但 Agent 已继续执行。专家说“恢复了”也需要符合该目标约定的验收条件，不能批量关闭相关问题。

测试包含重复回流、错误问题绑定、过期授权、专家与员工反馈冲突、恢复时服务仍故障，以及专家已执行动作后 Agent 不重复执行。

## 10 扩展四：接入真实企业系统

保留业务工具契约，把模拟适配器替换成真实只读或写入适配器；不让模型拿到通用管理凭据。接入前逐项确认真实系统身份映射、服务账号权限、审批语义、操作幂等与查询收据方式。

真实系统可能无法与本地数据库组成同一事务，因此“最多一次效果”不能只靠本地去重表保证。需要供应商幂等键、可核查外部请求 ID 或执行后对账；不具备这些条件的动作应限制自动重试，并保留 uncertain 状态。

真实 ITSM 还涉及通知、责任团队、访问范围与故障恢复。生产设计可以进一步加入队列、审计保留、凭据轮换和运行告警，但这些不是当前模拟版已经具备的能力。

## 11 实现时的优先顺序与裁剪影响

设计完整不等于一次实现所有扩展。建议先建立一个真实模型驱动的纵向链路，再扩展场景和异常；不能一直增加功能，最后才检查它们能否协同工作。

| 顺序 | 应得到的可检查结果 | 如需缩减，应明确的影响 |
| --- | --- | --- |
| 1 | 登录、一个问题、真实查询与状态保存 | 缺少这一层，后续演示难以证明真实端到端行为 |
| 2 | 受控写操作、核查、失败与交接 | 缺失会退化成指导型助手，不满足已选产品范围 |

优先裁剪非必要的视觉装饰、数据数量、额外模型对比和扩展功能。若必须裁剪已确认的核心能力，应先说明其影响并修订范围。这里不预先承诺一两天一定完成；接入、模型稳定性与异常调试需要以实际进展评估。

## 12 最终 README 建议结构

README 应让未参与讨论的人能够启动并评价项目：先说明能做什么与边界，再给运行命令、环境变量、演示账号和重置方法，然后解释架构、来源、评估命令、真实结果及已知失败。

凭据使用 .env.example 中的变量名，实际密钥不进入仓库、提示词或调试页面。说明支持的正常模式、关键词降级与 fixture 模式，以及各模式可以证明什么。

交付时链接这组详细材料，README 本身保持可读。所有性能和准确率数字来自保存的运行，不用设计目标填充结果表。
